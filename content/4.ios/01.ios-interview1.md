这篇文章偏“高频面试题 + 原理”，重点放在 iOS 上最容易踩坑的几类知识：内存管理、线程、RunLoop、UI 渲染和架构。准备面试时，最好把每个点说成“定义 + 场景 + 典型坑”。

## ARC 和内存管理

### ARC 是什么

ARC（Automatic Reference Counting）是 Swift / Objective-C 的自动引用计数机制。对象在被强引用时，引用计数 +1；引用释放时，引用计数 -1；当计数减到 0，对象就会被销毁。

关键点：

- `strong`：默认引用，增加引用计数
- `weak`：不增加引用计数，引用对象释放后会自动置为 `nil`
- `unowned`：不增加引用计数，但对象释放后访问会崩溃

```swift
class Person {
    var name: String
    init(name: String) { self.name = name }
    deinit { print("Person deinit") }
}

class Room {
    var person: Person?
}

var person: Person? = Person(name: "Tom")
var room: Room? = Room()
room?.person = person
person = nil
// 这里 person 被释放，但 room 持有它，直到 room 被释放
```

### 典型坑：循环引用

最常见的面试题是：`delegate`、`closure`、`timer` 等容易造成循环引用。

```swift
class A {
    var b: B?
}

class B {
    var a: A?
}
```

如果 `A` 持有 `B`，`B` 又持有 `A`，它们永远不会释放。解决方式：

- `weak` 打破一端
- `captureList` 让闭包不强持有 `self`

```swift
class VC {
    var timer: Timer?

    func start() {
        timer = Timer.scheduledTimer(withTimeInterval: 1, repeats: true) { [weak self] _ in
            guard let self else { return }
            print(self)
        }
    }
}
```

::note
面试里经常问：为什么 `weak` 比 `unowned` 安全？因为 `weak` 在对象释放后自动置为 `nil`，而 `unowned` 不会校验，错误访问会崩溃。只有在“对象生命周期明确不可能释放”的场景里才更适合用 `unowned`。
::

## weak、unowned、strong 的区别

| 关键字 | 引用计数 | 释放后行为 | 适用场景 |
| --- | --- | --- | --- |
| `strong` | +1 | 释放后不再存在 | 普通属性持有 |
| `weak` | 不加 | 自动变 `nil` | 代理、控制器引用、父子互相引用 |
| `unowned` | 不加 | 直接崩溃 | 明确不会释放的引用，常见于 `self` / `x` 之类 |

常见判断逻辑：

- 需要对象“有可能消失”，用 `weak`
- 需要对象“绝对不会消失”，用 `unowned`
- 普通持有关系，用 `strong`

::warning
`deinit` 只在对象真正释放时触发，循环引用会导致对象不停留在内存里，所以很多面试问题都从这里切入。
::

## RunLoop 是什么

RunLoop 是一个事件循环机制，用来处理事件、输入、定时器和端口消息。主线程的 RunLoop 会一直跑，让应用保持响应。

### 关键作用

- 让线程持续工作
- 处理输入事件、睡眠、唤醒
- 执行定时器和系统事件

### 为什么它重要

很多卡顿问题都和 RunLoop 有关系：

- UI 事件需要在主线程处理
- 定时器如果在主线程被阻塞，界面会卡住
- 长时间同步任务会让 RunLoop 停止处理事件

`mainRunLoop` 的生命周期和 App 运行周期绑定，App 进后台、前台切换时，RunLoop 的模式也会变化。

### 常见面试点

- `Timer` 依赖 RunLoop
- 如果在后台线程创建定时器，必须有对应的 RunLoop 运行
- `performSelector` 也依赖 RunLoop

```swift
Timer.scheduledTimer(withTimeInterval: 1.0, repeats: true) { _ in
    print("tick")
}
```

这里的定时器不是“独立线程”，而是由 RunLoop 驱动。

## GCD 与线程模型

### 串行队列 vs 并发队列

- 串行队列：一个任务结束后，再执行下一个，适合“顺序执行”
- 并发队列：多个任务可以同时执行，适合“任务分发”
- 主队列：串行队列，负责 UI 更新

```swift
let queue = DispatchQueue(label: "serial")
queue.async {
    print("task 1")
}
queue.async {
    print("task 2")
}
```

如果在串行队列中连续加任务，输出顺序稳定；但并发队列不能保证顺序。

### 同步和异步的区别

- `sync`：当前线程等待任务完成
- `async`：当前线程立即返回，不阻塞当前线程

重点记忆：

- `main.sync` 很危险，容易死锁
- `async` 通常用于异步网络、文件、后台计算

### barrier / group

常见面试题：

- `DispatchGroup`：等多个任务一起完成
- `DispatchBarrier`：并发队列中的写入同步拦截
- `DispatchSemaphore`：控制并发数量，常用于限流

```swift
let group = DispatchGroup()
group.enter()
DispatchQueue.global().async {
    sleep(2)
    print("task 1 done")
    group.leave()
}

group.notify(queue: .main) {
    print("all done")
}
```

::note
面试里最容易被问住的是：`async` 不等于多线程；它只是“把任务交给队列去执行”，是否开新线程要看底层分发情况。
::

## UIView、CALayer 与渲染

### UIView 是什么

`UIView` 是屏幕上的可视对象，负责事件处理、布局、绘制和层级管理。它本身并不直接负责最终像素绘制，真正负责绘制的是 `CALayer`。

- `UIView` 负责交互与控制
- `CALayer` 负责内容、动画、阴影、边框等

### 为什么一些动画很卡

`shadow`、`cornerRadius`、`mask`、`opacity` 等属性经常触发离屏渲染。离屏渲染会导致：

- GPU 额外计算
- 一帧耗时增加
- 卡顿、掉帧更明显

常见优化手段：

- 避免大面积圆角和阴影叠加
- 把高成本效果放在静态层
- 对复杂页面做 `shouldRasterize` 之类的控制（要谨慎）
- 使用 `layer.shouldRasterize` / `shadowPath` 作为极端优化手段

::tip
面试里常考：`UIView` 和 `CALayer` 的关系。最好记成：UI 提供控制，Layer 提供渲染与动画能力。
::

## MVC、MVVM 与架构

### MVC 是什么

MVC（Model-View-Controller）是最经典架构：

- Model：数据和业务逻辑
- View：界面
- Controller：协调二者

问题在于：在 UIKit 中，`UIViewController` 往往同时负责“显示”和“逻辑”，容易变得大而全。

### MVVM 怎么解决

MVVM（Model-View-ViewModel）：

- View 只负责展示
- ViewModel 负责转换数据与状态
- Model 负责数据层

优点：

- 逻辑更容易测试
- 控制器更轻
- UI 状态更容易管理

```swift
struct UserViewModel {
    let name: String
    let avatarURL: URL?
}
```

`ViewController` 只负责绑定数据和触发事件，真正的业务推导放在 `ViewModel` 里。

### 面试里常见问法

- “为什么 MVC 在 iOS 里容易臃肿？”
- “MVVM 相比 MVC 的改善点？ ”
- “什么时候该用 MVVM，而不是单纯的 Controller 逻辑？”

答案通常是：

- 页面逻辑复杂时，MVC 会让控制器承担太多职责
- MVVM 让控制器只负责交互和生命周期
- 复杂业务时更容易持续迭代和维护

## `loadView`、`viewDidLoad`、`viewWillAppear` 这些时机

这是 iOS 面试非常经典的基础题。

- `loadView`：创建根视图
- `viewDidLoad`：视图已加载，适合一次性初始化
- `viewWillAppear`：即将显示，适合刷新状态
- `viewDidAppear`：已经显示，适合动画或埋点
- `viewWillDisappear`：即将隐藏
- `viewDidDisappear`：已经隐藏

### 典型用法

```swift
override func viewDidLoad() {
    super.viewDidLoad()
    setupUI()
}

override func viewWillAppear(_ animated: Bool) {
    super.viewWillAppear(animated)
    updateData()
}
```

面试里经常问：在 `viewDidLoad` 和 `viewWillAppear` 里做什么？

- 一次性界面配置：`viewDidLoad`
- 每次进入页面时刷新：`viewWillAppear`

## 卡顿和性能

### 在 iOS 中，卡顿通常分三类

1. 主线程阻塞：网络、数据库、复杂计算、死循环
2. UI 层级过深：大量约束、复杂布局
3. 渲染过重：离屏渲染、阴影、layer 处理过多

### 常见优化方向

- 异步把耗时任务从主线程移走
- 使用 `UITableView` / `UICollectionView` 的重用机制
- 避免重绘和高频布局
- 图片做合适的解码和缓存
- 复杂列表尽量减少 `layoutIfNeeded` 和频繁 `reloadData`

::warning
如果一个页面很容易出现卡顿，不要只看 UI 层，往往是网络解码、图片处理、复杂布局和渲染叠加造成的，不要只把问题归咎到某一个单点。
::

## 结论

iOS 面试最重要的不是背概念，而是能把“概念”和“场景”连起来讲清楚。比如：

- ARC：为什么会循环引用，怎么用 `weak`
- GCD：为什么 `main.sync` 容易死锁
- RunLoop：为什么定时器依赖它
- UI：为什么离屏渲染会掉帧
- 架构：为什么 MVC 在大页面里容易膨胀，而 MVVM 更适合大项目

如果你准备面试，最有效的方式不是背一整套答案，而是对每个知识点准备 3 个问题：

1. 它是什么？
2. 用在什么场景？
3. 它的坑是什么？

这样回答会比“背书式模板”更有说服力。
